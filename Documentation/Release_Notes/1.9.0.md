# 1.9.0 — UNRELEASED

In development on the `1.9.0` branch. `main` carries the released 1.8.0 line.

## The goal of this cycle: the artefact, not the repository

This project verifies its source exhaustively. Twenty-two recorded defects, one
per check, each known to be rejected. A hundred and thirty-six citations that
must resolve. Two integer backends that must agree bit for bit. A harness that
refuses to meet its own exit criterion below sixty checks.

**All of it stops at the repository boundary.**

What a user actually receives is a `.crate` from crates.io or a tarball from a
GitHub release, and nothing checks either of them. `fixtures/SHA256SUMS` is
signed with the project's key; the `SHA256SUMS.txt` attached to every release is
not, and has never been. Nine release notes have carried the line:

> **The signing key has no authority behind it that is not the author**, and the
> release checksums are not signed.

The first half is a fact about the world and cannot be fixed from here. **The
second half is a fact about this repository and can be.**

The asymmetry is the point. A reader who wants to check a claim about the
*source* has more mechanism available than they could use; a reader who
downloads a *binary* has a checksum file anyone could have written.

### Scope

**C1 — sign the release checksums.** `SHA256SUMS.txt` gets a detached minisig,
attached to the release beside it, verifiable with the key already published in
five places. The same key, the same procedure, the same `minisign -V` incantation
the conformance vectors already document.

**This one needs the author.** The secret key is laptop-only with an offline
backup and must never enter the repository or CI, so the signature is produced at
release time by a person. The deliverable here is everything except that: the
workflow attaching the file, the documented procedure, and a `verify` path that
tells a downloader what to run.

**Stop if** the signature cannot be produced without the key reaching CI. Then
the honest outcome is a documented manual step and a release note saying the
artefacts are signed by hand, which is worth less than automation and more than
nothing.

**C2 — notice when a cited URL rots.** `check-links` is deliberately not in CI: a
job that fails when somebody else's web server is down trains people to ignore
red. The cost has been stated in every release note since — *nothing automatic
notices when a cited URL rots* — and two had already rotted when the command was
written.

A **scheduled** job has neither problem. It cannot block a push, it fails on its
own account, and a weekly result is exactly the resolution this question needs.

**Stop if** the schedule proves noisy enough to be ignored — if the archive host
is down often enough that the job cries wolf, the finding is that link-checking
against third parties is not automatable and the manual step stands.

**C3 — verify what was published.** Nothing confirms that the crate on crates.io
matches the tag it claims to come from. `xtask publish` runs the release and then
stops; no step downloads the result and compares it.

A `verify-release` that takes a version and checks: the published `.crate`
against what `cargo package` produces at that tag, the release binaries against
`SHA256SUMS.txt`, and `SHA256SUMS.txt` against its signature. Three artefacts,
three comparisons, none of which exists today.

**Stop if** `cargo package` is not reproducible enough to compare — timestamps
and file ordering may make a byte-for-byte match impossible. Then the check
becomes *the file list and the content hashes of the sources*, which is weaker
and still answers the question a reader is asking.

### Done when

A downloader can verify every artefact this project publishes, or the release
notes say which one they cannot and why.

### Explicitly not in scope

- **Anything breaking.** `cargo semver-checks` runs against the published 1.8.0.
- **The 2.0 decision.** [`A2`](../Proposals/A2-the-2.0-diff.md) produced the
  number in 1.8.0 and [`ROAD-TO-2.0.md`](../Proposals/ROAD-TO-2.0.md) carries it.
  The go/no-go is the author's and is not this cycle's work.
- **Reproducible builds.** Byte-identical binaries across machines is a much
  larger problem than checking that the bytes published match the bytes built.
  C3 is the second thing, not the first.
- **W3, the third locale**, still postponed pending a choice of language.

## Verification

```
cargo test --workspace --release
cargo test --workspace --exclude xtask --release --no-default-features \
  --features bigint,std,ucal-civil/hifitime,ucal/civil,ucal/body,ucal/events,ucal/cosmo
cargo test -p ucal --release --features full
RUSTFLAGS="-D warnings" cargo build --workspace --all-targets --release
cargo build -p ucal-core --target wasm32-unknown-unknown \
  --no-default-features --features u512
# Rebuild the binary the documentation is generated from: the --all-targets
# build above replaces it with one that has no `tui`, and check-docs and corpus
# both run it.
cargo build --release --locked -p ucal --features full
cargo run -p xtask && cargo run -p xtask -- lint \
  && cargo run -p xtask -- check-docs && cargo run -p xtask -- corpus \
  && cargo run -p xtask -- verify-vectors
```

At the opening: 609 tests on the default backend, 221 in `ucal` built with
`--features full`, 560 on bigint reaching the same Rule W digest over ten
thousand generated inputs, 22 corpus mutations with no survivors, `-D warnings`
clean across all targets with and without `full`, wasm `no_std` green, the UC-P0
constants harness meeting its exit criterion on both routes, lints clean across
77 files, nine `check-docs` checks passing and each held to a floor, 25 spec
deltas recorded with 24 standing and applied, 136 citations resolving across
source and documentation, fourteen cited URLs reaching their documents, MSRV 1.88
verified on the workspace and on `--features full`, 22 feature combinations
building, and all six crates clean under `cargo semver-checks` against the
published 1.8.0.

  that is not `derived:`.
