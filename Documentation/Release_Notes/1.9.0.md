# 1.9.0 — UNRELEASED

In development on the `1.9.0` branch. `main` carries the released 1.8.0 line.

## The goal of this cycle: the artefact, not the repository

This project verifies its source exhaustively. Twenty-two recorded defects, one
per check, each known to be rejected. A hundred and thirty-six citations that
must resolve. Two integer backends that must agree bit for bit. A harness that
refuses to meet its own exit criterion below sixty checks.

**All of it stops at the repository boundary.**

What a user actually receives is a `.crate` from crates.io or a tarball from a
GitHub release, and nothing checks either of them. `fixtures/SHA256SUMS` is
signed with the project's key; the `SHA256SUMS.txt` attached to every release is
not, and has never been. Nine release notes have carried the line:

> **The signing key has no authority behind it that is not the author**, and the
> release checksums are not signed.

The first half is a fact about the world and cannot be fixed from here. **The
second half is a fact about this repository and can be.**

The asymmetry is the point. A reader who wants to check a claim about the
*source* has more mechanism available than they could use; a reader who
downloads a *binary* has a checksum file anyone could have written.

### Scope

**C1 — sign the release checksums.** `SHA256SUMS.txt` gets a detached minisig,
attached to the release beside it, verifiable with the key already published in
five places. The same key, the same procedure, the same `minisign -V` incantation
the conformance vectors already document.

**This one needs the author.** The secret key is laptop-only with an offline
backup and must never enter the repository or CI, so the signature is produced at
release time by a person. The deliverable here is everything except that: the
workflow attaching the file, the documented procedure, and a `verify` path that
tells a downloader what to run.

**Stop if** the signature cannot be produced without the key reaching CI. Then
the honest outcome is a documented manual step and a release note saying the
artefacts are signed by hand, which is worth less than automation and more than
nothing.

**C2 — notice when a cited URL rots.** `check-links` is deliberately not in CI: a
job that fails when somebody else's web server is down trains people to ignore
red. The cost has been stated in every release note since — *nothing automatic
notices when a cited URL rots* — and two had already rotted when the command was
written.

A **scheduled** job has neither problem. It cannot block a push, it fails on its
own account, and a weekly result is exactly the resolution this question needs.

**Stop if** the schedule proves noisy enough to be ignored — if the archive host
is down often enough that the job cries wolf, the finding is that link-checking
against third parties is not automatable and the manual step stands.

**C3 — verify what was published.** Nothing confirms that the crate on crates.io
matches the tag it claims to come from. `xtask publish` runs the release and then
stops; no step downloads the result and compares it.

A `verify-release` that takes a version and checks: the published `.crate`
against what `cargo package` produces at that tag, the release binaries against
`SHA256SUMS.txt`, and `SHA256SUMS.txt` against its signature. Three artefacts,
three comparisons, none of which exists today.

**Stop if** `cargo package` is not reproducible enough to compare — timestamps
and file ordering may make a byte-for-byte match impossible. Then the check
becomes *the file list and the content hashes of the sources*, which is weaker
and still answers the question a reader is asking.

### And a second half: the tool people actually use

Added to the cycle after it opened, deliberately and on the record. The C-series
is about what this project *ships*; the F-series is about what it *is* to use.
They have nothing to do with each other, and a cycle carrying both is two cycles
wearing one number — which is a thing this project would catch in someone else's
work, so it is written down here rather than left to be inferred from the commit
log.

**F2 — stdin.** No command reads it. Every conversion is one process for one
timestamp, so `ucal` cannot appear in a pipeline at all. `-` as an instant reads
lines and emits one document per line.

**F1 — file-defined calendars become first-class.** `cal derive --anchor --at`
can produce a date from a pair of files, and then that calendar is stranded:
`show`, `between` and `cal show` know only the compiled-in registry. Z1 named
this as what *"use whatever celestial body"* asks for most directly.

**F5 — `h` and `min` in body files.** The fact sheets this project cites more
than any other publish rotation periods **in hours**. An author must convert by
hand, and Rule C asks for the published value *verbatim* — so the format
currently forces a small violation of the rule it exists to enforce.

**F6 — `ucal seq`**, instants at a tier interval. A `seq` for time, and the
thing F2 makes worth having.

**F9 — more bodies.** Uranus, Neptune, Pluto and Ceres are citable from sources
already in the tree. Every one added without the mechanism moving is more
evidence for Rule K.5's claim that Earth is an ordinary instance.

**F10 — the wall clock's chrome follows `--locale`.** `gagarin`'s Cyrillic is
hardcoded, which makes it the one place a theme overrides a user's flag. Tier
*names* were fixed in 1.5.0; the chrome was left.

**F4 — `ucal cal validate <file>`**. Today the only way to test a file is to run
`cal derive` and see whether it errors, which conflates *this file is malformed*
with *no calendar follows from this body*.

**F3 — Z2's remaining wall-clock items**: `--tier`, several dials, `--since`.

### Done when

A downloader can verify every artefact this project publishes, or the release
notes say which one they cannot and why — **and** the F-series has landed or been
recorded as dropped with a reason.

**C1, C2 and C3 gate the release.** No 1.9.0 is cut until a downloader can check
what they downloaded.

**The gate is met.** C1 is `xtask -- sign-release`, C2 is
[`links.yml`](../../.github/workflows/links.yml) with its notification rehearsed
twice, C3 is `xtask -- verify-release` with its failure path injected. All eight
F-items landed: F2, F1, F5, F6, F9, F10, F4, F3.

One thing remains and is not automatable: **the signature over 1.9.0's
`SHA256SUMS.txt` is produced at release time by the author**, because the key is
laptop-only and must never reach CI. Until that command is run against the
finished release, `verify-release 1.9.0` will report comparison 3 as `--` and
exit 5 — which is the check working, not a gap in it.

### Explicitly not in scope

- **Anything breaking.** `cargo semver-checks` runs against the published 1.8.0.
- **The 2.0 decision.** [`A2`](../Proposals/A2-the-2.0-diff.md) produced the
  number in 1.8.0 and [`ROAD-TO-2.0.md`](../Proposals/ROAD-TO-2.0.md) carries it.
  The go/no-go is the author's and is not this cycle's work.
- **Reproducible builds.** Byte-identical binaries across machines is a much
  larger problem than checking that the bytes published match the bytes built.
  C3 is the second thing, not the first.
- **W3, the third locale**, still postponed pending a choice of language.

## Added

- **Uranus, Neptune and Pluto** (F9). Fifteen calendars now, twelve derived
  bodies plus three. All three quote the fact sheet **in hours**, which F5 made
  possible in the same cycle, and Uranus and Pluto are retrograde — a sign
  `Measured` cannot carry (item 3 of the 2.0 bundle) and does not need to here,
  because the sheet publishes the length of day directly, so the solar day is
  stated rather than derived.

  They moved a finding. W4 step 1 established that every unit of every body sits
  on `T1` or `T2`; a Plutonian year is 248 Earth years against a `T3` span of 45,
  so the answer is now **three rungs out of forty-five** for the whole solar
  system. Better measured, not weakened.
- **`ucal seq`** (F6): instants at a tier interval, one per line. `seq` for time,
  and the thing F2 makes worth having —
  `ucal seq A B --step T1 | ucal to-civil -` is a pipeline this program could not
  express at all before. The output is lines rather than a document, for the same
  reason `completions` is: a generator's output is an input to something else.

  The count is computed **before** anything is printed and a walk over the cap is
  refused with the number it would have produced. One tick across one second is
  1.8 × 10⁴³ lines, and a program that starts printing and never stops is worse
  than one that says why.
- **`h` and `min` units in body files** (F5). Rule C asks for the published value
  *verbatim*, and the fact sheets this project cites more than any other print
  rotation periods in **hours** — `data::jupiter` converts one in a comment,
  `9.9250 h × 3600 = 35 730 s, exact`, which a file could not do. An author had
  to convert by hand: either a rounding, and a rounded parameter is a different
  calendar, or an exact conversion whose working the file no longer shows.

  A file quoting Jupiter's fact sheet in hours now derives `68/81`, which is what
  the hand-converted shipped body derives, and a test says so.
- **`ucal cal validate <calendar-id>` and `--all`** (G5), and with them a
  measurement of this project's own data.

  F4 built the precision probe and pointed it only at files somebody else wrote.
  The fifteen shipped calendars quote published figures under the same Rule C and
  are exactly as subject to the answer, and nothing had asked them. The command
  now takes a calendar id as well as a path — same code, one differing row, since
  a compiled-in calendar has no file to be well-formed.

  **The survey: fifteen calendars rest on nineteen distinct published figures,
  and the last digit of fourteen of them decides a leap rule outright.**

  That is not a defect and reads like one, so: a leap rule is a convergent of a
  continued fraction, continued fractions are violently sensitive to their
  inputs, and `CLI.md` has said exactly that in words since 1.4.0. This is that
  sentence with a number under it.

  **The finding worth having is the sharing.** A satellite's year *is* its
  primary's orbit, so Jupiter's `4332.589 d` is the orbital period of five
  calendars — `jupiter-d`, `io-d`, `europa-d`, `ganymede-d`, `callisto-d` — and
  its last digit decides all five leap rules at once. Saturn's `10759.2058 d`
  carries two more. A revision to one published figure moves five calendars, and
  nothing in this project said so before now.

  **And the probe is not comparable between bodies**, which the survey states
  rather than letting a reader assume otherwise. One unit in the last place is a
  whole second for Earth's `86400 s` and a millisecond for Mars's `88775.244 s`.
  `sensitive` means *at the precision this source published*; Earth's solar day
  is exact by definition and has no last digit to be wrong in, and is reported
  sensitive because a second either way does change the rule.

  The counts are asserted in a test, for the reason W4's were: a finding nobody
  can notice changing is a finding that will change. The first version of that
  test caught its own arithmetic — it counted parameter *slots* and reported
  nineteen sensitive out of nineteen distinct figures, five of them one figure
  counted five times.

  **G4 extended it to the figure that decides a calendar's cycle** — the grouping
  satellite's orbital period, which the probe did not reach. It reports **a depth,
  not a rule**, and the difference is the whole design: a leap rule is selected by
  a drift bound, so *which rule* can survive a nudge, while nothing selects a
  cycle and the deepest convergent is the ratio itself. Comparing chosen cycles
  could only ever print `sensitive`. What carries information is where the
  continued fraction diverges — terms that agree are candidate cycle rules that
  agree. Earth's survives seven terms.

  **And it says `cycle`, never `month`.** A Gregorian month is 28, 29, 30 or 31
  days and has not tracked the Moon for centuries, so borrowing the word for a
  synodic period would import an Earth *administrative* structure to describe a
  physical one. D-A5 already says it: *"month-like" is an Earth predicate.* The
  first draft of this feature used "month" throughout and had to be undone.

  **It also found a real inconsistency.** Which satellite groups a calendar is
  the **calendar's declaration** and not a property of the body — `mars-d`
  declares none although Mars has Phobos and Deimos. The first version read
  `satellites().first()` and so reported `cal validate mars-d` as *grouped by
  phobos* while `cal show mars-d` correctly said *no grouping satellite*. One
  calendar, two answers, because a declaration existed and the check went round
  it. A §15.1 file has nowhere to declare one, so a file keeps the first-listed
  rule; the two sources now differ deliberately and say which they are using.
- **`xtask -- sign-release <version>`** (C1): the release checksums are signed.
  `SHA256SUMS.txt` had never been, and nine release notes carried the same
  sentence about it. It was generated by the CI job that produced the files it
  describes, so it showed a download had arrived intact and nothing more —
  a checksum file anyone could have written.

  **The signature is produced by a person and cannot be otherwise.** The secret
  key is on one laptop with an offline backup and must never enter this
  repository or a runner. A signature CI could produce would attest to a GitHub
  secret, which is a different claim from the one this project makes about
  `fixtures/SHA256SUMS.minisig` — and a weaker one wearing the same shape is
  worse than none. C1 anticipated this and named the outcome: *a documented
  manual step and a release note saying the artefacts are signed by hand, which
  is worth less than automation and more than nothing.*

  So the step is one command. It downloads the checksum file CI attached, signs
  it with a trusted comment naming the tag, **verifies the signature against
  `fixtures/ucal.pub` before uploading anything**, and attaches it. It refuses to
  sign a checksum file that names no files — a valid signature over nothing is
  the exact shape of evidence this project exists to refuse — and refuses to
  re-sign one that already has a signature.

  Releases before 1.9.0 will not be signed retrospectively. Signing a 2026
  checksum file today would say a key vouched for it today, which is not the
  claim a reader would take from it.
- **`xtask -- verify-release <version>`** (C3): three comparisons, none of which
  existed. The published `.crate` files against a checkout of the tag, the
  release binaries against `SHA256SUMS.txt`, and that file against its
  signature.

  **It checks the tag out itself.** The first run was made from a 1.9.0 tree
  against the published 1.8.0 and reported five failures — every one of them
  cargo correctly refusing to resolve `^1.9.0` against an index that does not
  have 1.9.0 yet. A check comparing the wrong tree and blaming the artefact is
  worse than no check, so it creates a detached worktree at the tag and says
  which commit it packaged.

  **C3's stop condition did not fire, and that is the finding.** It expected
  `cargo package` not to be reproducible — *timestamps and file ordering may
  make a byte-for-byte match impossible* — and planned a fallback to comparing
  file lists and content hashes. All six crates published for 1.8.0 are
  **byte-for-byte identical** to what `cargo package` produces from `v1.8.0`;
  cargo normalises the mtimes. The fallback is implemented and reported when the
  strong answer fails, because a future cargo may stop normalising, but it has
  never fired.

  Verified strict by injecting the defect it exists to catch: one added byte in
  `ucal-core/src/lib.rs`, in a checkout of the tag, and the check named that file
  and `.cargo_vcs_info.json` while the other five crates still passed. The
  network makes it ineligible for the offline defect corpus, so it takes an
  `UCAL_RELEASE_TREE` seam whose only purpose is to make that injection possible
  — and the checksum comparison is split so its logic is unit-tested offline in
  five cases, including the empty-file floor.

  A comparison that could not be performed is `--` and exits 5, never 0. A check
  that could not run has not passed.
- **Three wall-clock items from Z2** (F3), which closes that proposal's list.

  **`--clock-local` repeats.** An airport wall:
  `--clock-local earth-d --clock-local mars-d`. Today that is the whole wall
  that can be built — a dial shows local fields, local fields need a phase, and
  two of the fifteen calendars have an anchor. The limit is a fact about anchors
  and not about the flag.

  **`--tier <T>` chooses the hero.** Z2 named the risk exactly — *"every choice
  but `T0` produces a screen where nothing moves, which is a stopped clock with
  extra steps"* — and the answer is to say so rather than to refuse, because
  refusing would refuse the flag's stated purpose. `T1` changes every 2 min 26 s
  and is still a clock; at `T2` and above the face prints **a calendar display:
  this hand does not move while you watch**. A hand that changes every 45 years
  is pixel-identical to a clock that has stopped, so it is labelled.

  **`--since <ORIGIN>` is an odometer**, read on the same ladder the hands are
  on — a tier is a duration, so an elapsed count divides by one exactly as an
  instant's does. The leading drum does not wrap: every other rung reads mod
  3125 like the face's hands, and without an unwrapped top drum the reading
  could not tell 2 000 years from 142 000. An origin in the future counts
  towards it and says `UNTIL`, because absolute time is unsigned (Rule B) and a
  direction beside a magnitude is what `SignedWindow` already does.

  **And it refuses**, which is the interesting part. `--since` takes an event id,
  and an event whose window is wider than the finest hand on the face is
  `UCAL-E0023`: `holocene` is uncertain by about two centuries, and an odometer
  ticking 66 000 times a second against that figure is theatre. `bridge-epoch` is
  the exception Z2 predicted — exact by declaration, zero window, and the one
  origin for which "time since" is a real reading. A test walks the whole
  catalogue in both directions, because a check that only ever refused would
  pass with the accept path broken.
- **`ucal cal validate <FILE>`** (F4): does this §15.1 file load, and does a
  calendar follow from it? **Two questions, and `cal derive` could only answer
  one.** A body whose year is a whole number of its solar days gets `UCAL-E0060`
  from `derive` — a fact about the body, not a defect in the file — and an author
  reading a red exit code cannot tell those apart. `validate` succeeds there and
  says which it is.

  The file may be either kind. A body file is tried first; an anchor file gets
  the anchor loader before any error is reported, because the strict body loader
  answers a perfectly valid anchor file with `UCAL-E0012`, *unknown key*, which
  is true and unhelpful.

  **And it measures the caveat this project has carried since 0.2.0.** Every
  release note says *a rounded parameter is a different calendar*; that was true
  and unmeasurable. For each measured parameter feeding the intercalation, the
  last published digit is moved by one in each direction and the rule re-derived.
  `Measured` holds its figure as a mantissa and a decimal count rather than as a
  parsed number — Rule Y.1, so `9.9250` round-trips — which makes one unit in the
  last place exactly `mantissa ± 1` and the probe exact rather than approximate.

  Europa's `orbital_period` comes back **sensitive**: `4332.589 d` gives `1/24`,
  its two neighbours give `5/119` and `7/169`. `CLI.md` had been advising authors
  to do this by hand — *"shorten the value until `cal derive` reports a different
  rule and then put a digit back"* — which is the shape this project keeps
  finding: a procedure written down, correct, and never mechanised.

  It reports and does not judge. Earth's `86400 s` solar day is sensitive too,
  because a second either way changes the calendar — and it is exact by
  definition, so it has no last digit to be wrong in. What the probe measures is
  whether *this* figure's precision decides *this* calendar. Whether that matters
  is a question about the source, and no program here can answer it.
- **`ucal show --body <FILE> --anchor <FILE>`** (F1): one calendar defined by
  §15.1 files, in the same table as the shipped ones, rendered by the same code
  path. This is the comparison the loaders exist for — `cal derive --anchor --at`
  could already produce that body's date alone; what it could not do was put it
  beside anything.

  `cal show` deliberately did **not** grow the same flags. `cal derive` already
  prints that view from the same code, and two spellings of one question is how
  they come to disagree. Found by trying it: clap could not disambiguate an
  optional id from a required instant, and the obstacle turned out to be pointing
  at a duplicate feature.
- **`-` reads instants from stdin** (F2). No command read it before, so every
  conversion was one process for one timestamp and `ucal` could not appear in a
  pipeline at all. Accepted by the four commands taking exactly one instant; with
  `--json` the output is **JSON Lines**, one record per line.

  A bad line is reported and **the stream continues**, and the exit status is
  still non-zero. Those pull in opposite directions on purpose: a filter that
  dies on line 3 of 10 000 has discarded 9 997 answers it already had, and one
  that exits 0 after skipping a line lets a script treat a partial run as
  complete.

## Changed

- **`check-links` runs on a schedule, and a failure opens an issue** (C2). The
  command has existed since 1.4.0 and had never run except when somebody
  remembered. Every release note since carried the cost in the same words —
  *nothing automatic notices when a cited URL rots* — and two locators had
  already rotted by the time it was written, **one of them answering `200 OK`**
  from a page that was not the cited document.

  Still not on `push`, for the reason it never was: somebody else's outage must
  not turn this repository red, because *CI green on every push with no
  known-failing job* is a 1.0 exit criterion and the way the last false
  criterion survived a whole release was nobody reading a red job. A scheduled
  job has neither problem — it cannot block a push and it fails on its own
  account.

  **The failure opens an issue**, and a later failure comments on the open one
  rather than opening a second. A job that fails into the Actions tab is a
  mechanism with nothing attached to it, which is the shape this project keeps
  finding in its own work: a claim with no mechanism, a mechanism with no wire,
  a schedule with no date.

  **And the wire was rehearsed rather than assumed.** `workflow_dispatch` takes
  a `rehearse` input that fails the check on purpose, because a run where
  nothing is wrong cannot prove a notification is delivered — the same
  discipline every other check here is held to. The first rehearsal found two
  defects in the notification: the issue body opened with forty lines of
  escape-coded `Downloading`, because `CARGO_TERM_COLOR: always` was copied from
  workflows whose output goes to a terminal and this one goes into an issue; and
  the verdict was buried under the dependency download that preceded it. Both
  fixed, then rehearsed again, which confirmed the second failure comments
  instead of filing a duplicate.

  The file is on `main` ahead of the 1.9.0 merge, because GitHub runs
  `schedule:` only on the default branch — a schedule sitting on a development
  branch is a schedule that never fires, which would have been this job's own
  failure mode reproduced inside the fix.

  **The stop condition is not yet answerable.** C2 says to stop if the schedule
  proves noisy enough to be ignored. All fourteen cited URLs currently resolve,
  so there is no noise to measure; the finding, if there is one, arrives in a
  later cycle.
- **The wall clock's chrome follows `--locale`** (F10). The Vostok panel's plates
  were hardcoded Cyrillic, so `--gagarin --locale en` drew Russian anyway: the
  one place in this program where a theme overrode a user's flag. Tier *names*
  were fixed in 1.5.0 and the chrome was left, with the mismatch written down in
  three places as intended behaviour — "the intended pairing is
  `--gagarin --locale ru`" — which is a documented bug, not a design.

  **The other six faces had the same bug and nobody called it one.** English
  chrome under `--locale ru` reads as a translation nobody finished rather than
  as a flag being ignored, so only the direction that looked wrong got reported.
  All seven faces are now translated whole, and a test walks every theme in both
  locales asserting that `--locale en` draws no Cyrillic and `--locale ru` draws
  some.

  **What does not follow the flag is the point of the change.** `VERB`, `NOUN`,
  `PROG`, `KEY REL` and `MONITOR DECIMAL · TIME` are the DSKY's own legends,
  printed on a panel in 1969; `Q TO DISENGAGE` and `T1 ARC` belong to their
  consoles the same way. Translating them would invent a Russian Apollo that
  never existed. The line is between *a sentence this program wrote*, which is
  translatable, and *a word the instrument bore*, which is a proper noun — and it
  is why `gagarin` loses nothing by giving its Cyrillic back to `--locale`.
