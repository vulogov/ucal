# 1.9.0 — UNRELEASED

In development on the `1.9.0` branch. `main` carries the released 1.8.0 line.

## The goal of this cycle: the artefact, not the repository

This project verifies its source exhaustively. Twenty-two recorded defects, one
per check, each known to be rejected. A hundred and thirty-six citations that
must resolve. Two integer backends that must agree bit for bit. A harness that
refuses to meet its own exit criterion below sixty checks.

**All of it stops at the repository boundary.**

What a user actually receives is a `.crate` from crates.io or a tarball from a
GitHub release, and nothing checks either of them. `fixtures/SHA256SUMS` is
signed with the project's key; the `SHA256SUMS.txt` attached to every release is
not, and has never been. Nine release notes have carried the line:

> **The signing key has no authority behind it that is not the author**, and the
> release checksums are not signed.

The first half is a fact about the world and cannot be fixed from here. **The
second half is a fact about this repository and can be.**

The asymmetry is the point. A reader who wants to check a claim about the
*source* has more mechanism available than they could use; a reader who
downloads a *binary* has a checksum file anyone could have written.

### Scope

**C1 — sign the release checksums.** `SHA256SUMS.txt` gets a detached minisig,
attached to the release beside it, verifiable with the key already published in
five places. The same key, the same procedure, the same `minisign -V` incantation
the conformance vectors already document.

**This one needs the author.** The secret key is laptop-only with an offline
backup and must never enter the repository or CI, so the signature is produced at
release time by a person. The deliverable here is everything except that: the
workflow attaching the file, the documented procedure, and a `verify` path that
tells a downloader what to run.

**Stop if** the signature cannot be produced without the key reaching CI. Then
the honest outcome is a documented manual step and a release note saying the
artefacts are signed by hand, which is worth less than automation and more than
nothing.

**C2 — notice when a cited URL rots.** `check-links` is deliberately not in CI: a
job that fails when somebody else's web server is down trains people to ignore
red. The cost has been stated in every release note since — *nothing automatic
notices when a cited URL rots* — and two had already rotted when the command was
written.

A **scheduled** job has neither problem. It cannot block a push, it fails on its
own account, and a weekly result is exactly the resolution this question needs.

**Stop if** the schedule proves noisy enough to be ignored — if the archive host
is down often enough that the job cries wolf, the finding is that link-checking
against third parties is not automatable and the manual step stands.

**C3 — verify what was published.** Nothing confirms that the crate on crates.io
matches the tag it claims to come from. `xtask publish` runs the release and then
stops; no step downloads the result and compares it.

A `verify-release` that takes a version and checks: the published `.crate`
against what `cargo package` produces at that tag, the release binaries against
`SHA256SUMS.txt`, and `SHA256SUMS.txt` against its signature. Three artefacts,
three comparisons, none of which exists today.

**Stop if** `cargo package` is not reproducible enough to compare — timestamps
and file ordering may make a byte-for-byte match impossible. Then the check
becomes *the file list and the content hashes of the sources*, which is weaker
and still answers the question a reader is asking.

### And a second half: the tool people actually use

Added to the cycle after it opened, deliberately and on the record. The C-series
is about what this project *ships*; the F-series is about what it *is* to use.
They have nothing to do with each other, and a cycle carrying both is two cycles
wearing one number — which is a thing this project would catch in someone else's
work, so it is written down here rather than left to be inferred from the commit
log.

**F2 — stdin.** No command reads it. Every conversion is one process for one
timestamp, so `ucal` cannot appear in a pipeline at all. `-` as an instant reads
lines and emits one document per line.

**F1 — file-defined calendars become first-class.** `cal derive --anchor --at`
can produce a date from a pair of files, and then that calendar is stranded:
`show`, `between` and `cal show` know only the compiled-in registry. Z1 named
this as what *"use whatever celestial body"* asks for most directly.

**F5 — `h` and `min` in body files.** The fact sheets this project cites more
than any other publish rotation periods **in hours**. An author must convert by
hand, and Rule C asks for the published value *verbatim* — so the format
currently forces a small violation of the rule it exists to enforce.

**F6 — `ucal seq`**, instants at a tier interval. A `seq` for time, and the
thing F2 makes worth having.

**F9 — more bodies.** Uranus, Neptune, Pluto and Ceres are citable from sources
already in the tree. Every one added without the mechanism moving is more
evidence for Rule K.5's claim that Earth is an ordinary instance.

**F10 — the wall clock's chrome follows `--locale`.** `gagarin`'s Cyrillic is
hardcoded, which makes it the one place a theme overrides a user's flag. Tier
*names* were fixed in 1.5.0; the chrome was left.

**F4 — `ucal cal validate <file>`**, and **F3 — Z2's remaining wall-clock
items**: `--tier`, several dials, `--since`.

### Done when

A downloader can verify every artefact this project publishes, or the release
notes say which one they cannot and why — **and** the F-series has landed or been
recorded as dropped with a reason.

**C1, C2 and C3 gate the release.** No 1.9.0 is cut until a downloader can check
what they downloaded.

### Explicitly not in scope

- **Anything breaking.** `cargo semver-checks` runs against the published 1.8.0.
- **The 2.0 decision.** [`A2`](../Proposals/A2-the-2.0-diff.md) produced the
  number in 1.8.0 and [`ROAD-TO-2.0.md`](../Proposals/ROAD-TO-2.0.md) carries it.
  The go/no-go is the author's and is not this cycle's work.
- **Reproducible builds.** Byte-identical binaries across machines is a much
  larger problem than checking that the bytes published match the bytes built.
  C3 is the second thing, not the first.
- **W3, the third locale**, still postponed pending a choice of language.

## Added

- **Uranus, Neptune and Pluto** (F9). Fifteen calendars now, twelve derived
  bodies plus three. All three quote the fact sheet **in hours**, which F5 made
  possible in the same cycle, and Uranus and Pluto are retrograde — a sign
  `Measured` cannot carry (item 3 of the 2.0 bundle) and does not need to here,
  because the sheet publishes the length of day directly, so the solar day is
  stated rather than derived.

  They moved a finding. W4 step 1 established that every unit of every body sits
  on `T1` or `T2`; a Plutonian year is 248 Earth years against a `T3` span of 45,
  so the answer is now **three rungs out of forty-five** for the whole solar
  system. Better measured, not weakened.
- **`ucal seq`** (F6): instants at a tier interval, one per line. `seq` for time,
  and the thing F2 makes worth having —
  `ucal seq A B --step T1 | ucal to-civil -` is a pipeline this program could not
  express at all before. The output is lines rather than a document, for the same
  reason `completions` is: a generator's output is an input to something else.

  The count is computed **before** anything is printed and a walk over the cap is
  refused with the number it would have produced. One tick across one second is
  1.8 × 10⁴³ lines, and a program that starts printing and never stops is worse
  than one that says why.
- **`h` and `min` units in body files** (F5). Rule C asks for the published value
  *verbatim*, and the fact sheets this project cites more than any other print
  rotation periods in **hours** — `data::jupiter` converts one in a comment,
  `9.9250 h × 3600 = 35 730 s, exact`, which a file could not do. An author had
  to convert by hand: either a rounding, and a rounded parameter is a different
  calendar, or an exact conversion whose working the file no longer shows.

  A file quoting Jupiter's fact sheet in hours now derives `68/81`, which is what
  the hand-converted shipped body derives, and a test says so.
- **`ucal show --body <FILE> --anchor <FILE>`** (F1): one calendar defined by
  §15.1 files, in the same table as the shipped ones, rendered by the same code
  path. This is the comparison the loaders exist for — `cal derive --anchor --at`
  could already produce that body's date alone; what it could not do was put it
  beside anything.

  `cal show` deliberately did **not** grow the same flags. `cal derive` already
  prints that view from the same code, and two spellings of one question is how
  they come to disagree. Found by trying it: clap could not disambiguate an
  optional id from a required instant, and the obstacle turned out to be pointing
  at a duplicate feature.
- **`-` reads instants from stdin** (F2). No command read it before, so every
  conversion was one process for one timestamp and `ucal` could not appear in a
  pipeline at all. Accepted by the four commands taking exactly one instant; with
  `--json` the output is **JSON Lines**, one record per line.

  A bad line is reported and **the stream continues**, and the exit status is
  still non-zero. Those pull in opposite directions on purpose: a filter that
  dies on line 3 of 10 000 has discarded 9 997 answers it already had, and one
  that exits 0 after skipping a line lets a script treat a partial run as
  complete.

## Verification

```
cargo test --workspace --release
cargo test --workspace --exclude xtask --release --no-default-features \
  --features bigint,std,ucal-civil/hifitime,ucal/civil,ucal/body,ucal/events,ucal/cosmo
cargo test -p ucal --release --features full
RUSTFLAGS="-D warnings" cargo build --workspace --all-targets --release
cargo build -p ucal-core --target wasm32-unknown-unknown \
  --no-default-features --features u512
# Rebuild the binary the documentation is generated from: the --all-targets
# build above replaces it with one that has no `tui`, and check-docs and corpus
# both run it.
cargo build --release --locked -p ucal --features full
cargo run -p xtask && cargo run -p xtask -- lint \
  && cargo run -p xtask -- check-docs && cargo run -p xtask -- corpus \
  && cargo run -p xtask -- verify-vectors
```

At the opening: 609 tests on the default backend, 221 in `ucal` built with
`--features full`, 560 on bigint reaching the same Rule W digest over ten
thousand generated inputs, 22 corpus mutations with no survivors, `-D warnings`
clean across all targets with and without `full`, wasm `no_std` green, the UC-P0
constants harness meeting its exit criterion on both routes, lints clean across
77 files, nine `check-docs` checks passing and each held to a floor, 25 spec
deltas recorded with 24 standing and applied, 136 citations resolving across
source and documentation, fourteen cited URLs reaching their documents, MSRV 1.88
verified on the workspace and on `--features full`, 22 feature combinations
building, and all six crates clean under `cargo semver-checks` against the
published 1.8.0.

  bundle is smaller than five cycles of deferral implied; item 1 alone has three

  sharpest sentence answered, and the delta unmoved.

  might close D-A20 without the `Cow` migration.

  compile-pass fixtures. Six further categories were probed in A3 and it handles
  all of them; the categories nobody has probed remain unprobed.
- **Three single-site conditions still share codes with other meanings** (D-A24).
- **A rounded parameter is a different calendar**, for every body-file parameter
  that is not `derived:`.
- **Ten of the twelve derived calendars have no anchor**, the ordinary case.
- **[`GE-U4-walk.sh`](../Proposals/GE-U4-walk.sh) is built, run, and waiting on
  two readers.**
- **W3, a third locale**, postponed with its reason recorded.
