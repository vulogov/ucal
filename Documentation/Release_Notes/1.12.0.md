# 1.12.0 — UNRELEASED

In development on the `1.12.0` branch. `main` carries the released 1.11.0 line.

## The goal of this cycle: *released* is a claim about the world

1.9.0's theme was **the artefact, not the repository**. 1.11.0's was **the
standard that stops at the edge of one build**. This cycle is where those two
meet, and it opens with three instances already found — none of them by a check,
and all three within two days of each other.

Every one has the same structure: **the repository did the work, wrote down the
outcome, and never asked the world whether the outcome happened.**

### The three known instances

**1.10.0 was marked released and exists nowhere.** The Contents table below said
*released — 2026-08-28*. There is no tag in any remote, no GitHub release, and
no crate on `crates.io`, which goes 1.9.0 → 1.11.0. The procedure has ten steps
and the first seven ran; the table was written on the strength of the cut. Found
by reading which baseline `cargo semver-checks` had chosen — it fetches the
newest *published* version and fetched 1.9.0, while 1.11.0's notes said in two
places that the comparison was against 1.10.0.

**v1.9.0 is unsigned, and 1.9.0's notes say it is the first release whose
binaries a downloader can check end to end.** The mechanism was built and is
correct: `sign-release` exists, the key was published in five places, and
`verify-release` checks the signature. The command was never run for that tag.
`verify-release 1.9.0` has been reporting `UNSIGNED` the whole time.

So **v1.11.0 is the first signed release**, and 1.9.0's sentence — repeated in
1.10.0's and 1.11.0's *Carried forward* sections, which is three notes carrying
one unchecked claim — was never true. It is now unfixable for a reason the
project already published: the key of that era is dead, and signing with today's
key would say a 2026-08-31 key vouched for a 2026-08-27 artefact, which is
precisely the claim [`spec/CONFORMANCE.md`](../../spec/CONFORMANCE.md) refuses
to make about pre-1.9.0 releases.

**`verify-release` has two standing failures and nothing reads it.** For v1.9.0,
five crates differ in `Cargo.lock`. For v1.11.0, six differ in
`.cargo_vcs_info.json` — because 1.11.0 published from the cut commit while the
tag sits on the merge, which the procedure did not say to avoid until it had
happened. Every other byte matches in both cases. A check that is known to fail
trains its reader to ignore it, and *CI green with no known-failing job* was a
1.0 exit criterion.

### Scope

**R1 — a version marked released must exist where a reader can get it.** For
every row in the Contents table not marked unreleased: the tag resolves on the
remote, a GitHub release exists for it, and every crate is on the registry at
that version. Network-dependent, so it belongs on a schedule beside
`check-links` and not on `push` — a check that reddens the tree because
`crates.io` is having a bad morning trains its reader to ignore it, which is the
defect this item is about.

**Stop if** it cannot distinguish *not published yet* from *published and gone*.
A release in progress must not be a failure, and a check that cannot tell those
apart would have to be run by hand at exactly the moment nobody is watching.

**R2 — `verify-release`'s standing failures are explained or fixed.** Two
different causes and probably two different answers. `.cargo_vcs_info.json` is
settled going forward and unfixable for 1.11.0, so it wants an enumerated
exception with its reason — the shape the retired signing key got, not a
silenced comparison. `Cargo.lock` is not understood yet and is the one to
measure first.

**Stop if** the `Cargo.lock` difference turns out to be cargo resolving
differently today than at publish time. Then the finding is that *`cargo package`
is byte-reproducible* — measured across two releases and stated in 1.9.0's
notes — was overclaimed, and the claim needs narrowing rather than the check
needing fixing.

**R3 — what makes a command reach the `ucal-json/1` promise.** Two
hand-maintained lists enumerate the same commands: `commands()` in
`json_surface.rs` and `all_commands()` in `manual_fields.rs`. Nothing checks
either is complete. `the_baseline_covers_every_command` checks that every
*listed* command contributes, which is the weaker half of the question.

1.11.0 found this the only way it can currently be found: `add --in` was added to
one list, and the *other* file failed, reporting a documented field no command
emitted. Seven commands are absent from the baseline today and every one of them
is legitimately absent — `cal`, `cosmo` and `events` are parents whose
subcommands are listed; `completions`, `man` and `help` emit roff and shell
rather than documents; `seq` emits bare lines under `--json` deliberately.
**Nothing establishes that.** A legitimate absence and an oversight are the same
thing to every check in the tree.

**Stop if** enumerating the commands mechanically needs the `clap` tree, which
these tests do not have and cannot get without shelling out to the binary — the
reason `manual_fields` is a test and not a lint. Then the answer is an explicit
list of *deliberately absent* commands with a reason each, which is worse than a
derivation and much better than nothing.

### Done when

Every claim this repository makes about a released artefact is either checked
against the world, or written down as a claim nobody checks.

## Added

- **[`Documentation/INTEROP.md`](../INTEROP.md)** (D) — how to consume
  `ucal-json/1` from another language.

  The division `S1` draws is that this project supplies exact time and a
  pipeline supplies the science. That only works if the seam is documented
  rather than inferred, and it was inferred: the JSONL streaming contract, the
  reason every number is a string, and which commands emit no document at all
  were each discoverable and nowhere stated.

  **Every number is a string because JSON's number type is a double in most
  parsers.** A tick count is 61 digits today and 155 at the ceiling; a parser
  that reads it as a number rounds it to 17 significant figures, which is the
  rounding this whole project exists to refuse. `int()` in Python is exact;
  `float()` undoes the format's entire purpose.

  **A stream is JSONL, one document per line**, not an array — an array must be
  complete before it is valid, which is not a filter.

  **A warning is data and does not change the exit code.** A pipeline that drops
  the field has discarded the part saying the number is being asked to do
  something its source does not support.

- **`ucal ephem`** (B) — a published linear ephemeris, **carrying the
  uncertainty it was published with**. `S1`'s flagship.

  Nearly every repeating astronomical event is published as `T(E) = T₀ + E·P`,
  and the useful answer is not `T(E)`. It is the window
  `± k·√(σ_T₀² + (E·σ_P)²)`, because that is what decides whether an
  observation is worth scheduling — and most tooling computes the centre and
  drops the width, so an observer books thirty minutes for an event predicted
  to ±forty.

  **The window grows, and that is the whole feature.** On the format example
  the half-width runs 7.5 s at the epoch, 33.7 s at cycle 1000, 164 s at cycle
  5000.

  **`UCAL-W0003` outside the fitted range**, which is the mistake people make
  *in print*: a 2015 fit applied thousands of cycles past its data.
  `fitted_cycles` is required in the file because it is the only field that
  makes the warning mean anything — without it every extrapolation looks
  exactly like an interpolation. Rule C forbids extrapolating *silently*, not
  extrapolating.

  **An uncertainty is carried when it is cited, and never when it is inferred.**
  That is the line this feature draws, and it is why `ucal-body`'s parameters
  still have none: the planetary sources do not uniformly publish one and a
  fabricated σ is worse than an absent one. For an ephemeris, `σ_P` is the
  headline number of the paper.

  **Quadrature assumes independence**, which a joint fit does not give. The
  convention of placing `T₀` near the centre of the data span exists precisely
  to minimise that correlation; where a source states a covariance this is an
  underestimate and the source's own window should be used. Stated because a
  window that is too narrow is the one failure mode this type exists to prevent.

  Bracketing is **outward** — `isqrt_ceil` on the quadrature sum, and a whole
  extra tick on each side — so nothing narrows by assumption. `Ṗ` is supported
  and acts through `E²`, so it pushes past and future cycles the same way.

  **This release ships no ephemerides**, and the reason is Rule C rather than
  effort: a shipped one must quote `T₀`, `P` and both σ verbatim from a paper,
  and a figure typed from memory is the defect `cal validate` found in this
  project's own `europa.hjson`. D5 reached the same conclusion about Titan's
  anchor and the answer there was *no anchor*. The format ships; the figures
  wait for somebody holding the papers.

- **`ucal dilate`** — gravitational time dilation at a radius, as a **certified**
  interval. `S2` proposed it and named the primitive: `isqrt_floor` and
  `isqrt_ceil` were already there.

  ```
  ucal dilate --rs-over-r 0.0000042467      # the Sun's surface
  ucal dilate --rs-over-r 0.35              # a neutron star
  ucal dilate --rs-over-r 999999/1000000    # just outside a horizon
  ```

  **Exactness earns its keep at the two ends, not in the middle.** Computing
  `z = 1/√(1−x) − 1` in `f64`, against the exact value:

  | | `r_s/r` | correct digits in `f64` |
  |---|---|---|
  | the Sun | 4.25 × 10⁻⁶ | **~8** of 16 |
  | Sirius B, a white dwarf | 1.15 × 10⁻⁴ | ~11 |
  | a neutron star | 0.35 | ~14 |
  | just outside a horizon | 0.999999 | **~1** |

  In the weak field `1/√(1−x)` is a hair above 1 and subtracting 1 throws away
  half the mantissa; near the horizon `1 − x` is itself the cancellation. The
  neutron star — the case that *sounds* like it needs care — is where a double
  does best. **So this is not only a black-hole tool**: the solar gravitational
  redshift is a measured quantity and white dwarf redshifts are how their masses
  are checked, and both sit where `f64` has already lost half its digits.

  `r_s/r ≥ 1` is refused: inside, the Schwarzschild radial coordinate is not a
  clock at all, which is a change in what the question means rather than a
  larger number. And it reports a **ratio between two clocks** without claiming
  either is the one `ucal` keeps — giving `UC-1` a stated frame is a 2.0
  question, because one unsigned integer per instant asserts there is one time.

- **`ucal from-jd` and `ucal to-jd`** (A1) — a Julian Date, in a named scale, as
  absolute time. The first item of
  [`S1`](../Proposals/S1-astrophysics-roadmap.md)'s astrophysics plan.

  **Every cited parameter in this project is indexed by JD in its source**, and
  J2000.0 — the epoch the whole body layer hangs on — *is* JD 2451545.0 TT.
  Until now, checking a shipped figure against the paper it came from was a hand
  operation.

  ```
  ucal from-jd 2451545.0 --scale tt        # J2000.0, exactly
  ucal from-jd 51544.5   --scale tt --mjd  # the same instant
  ucal from-jd 2460000.5 --scale tdb       # a window, not a point
  ```

  **`--scale` is required and has no default, permanently.** `TT − TAI` is
  32.184 s exactly and `TT − UTC` is 69.184 s today and changes without warning;
  a converter that defaults is silently wrong by 69 seconds whenever it guesses,
  and a 69-second error is invisible in a light curve and fatal in a pulsar
  residual. Rule C's habit — a value without its provenance is not a value —
  applied to the time scale.

  **`tdb` answers with a window, and that is the honest answer.** `TDB − TT` is
  a periodic series whose evaluation is floating point, which Rule E forbids in
  a shipped crate. Rather than ignoring a 1.7 ms difference or importing a
  series, the conversion carries the series' **bound**, ±1.7 ms, rounded
  outward — because a bound rounded inward is not one. Rule U: the window is the
  value, and a zero-width window and a ±1.7 ms one are the same kind of answer.

  **Two scales are refused with reasons rather than approximated.** `utc`,
  because a Julian Date counts days of 86400 SI seconds and a UTC day containing
  a leap second has 86401, so `JD(UTC)` is not a uniform day count — the error
  points at `from-civil --scale utc`, which has the leap table. And `ut1`,
  because it needs ΔUT1, an observed IERS quantity this repository does not
  carry and Rule C will not let it invent.

  Exact in both directions, and `UCAL-E0043` rather than a rounding for a date
  needing more than the ~34 decimal places a tick can express.

- **`cargo run -p xtask -- check-releases`** (R1) — every version the Contents
  table marks *released* has a tag on the remote, a GitHub release, and all six
  crates on the registry.

  **1.10.0's row said `released` and 1.10.0 existed nowhere.** Nothing noticed
  for three days and nothing would have, because every other check in this tree
  reads files that are in it. *Released* is a claim about the world.

  **Scheduled daily, not on `push`** — `links.yml`'s reasoning, and the schedule
  is tighter for a reason it does not share: a rotted URL rots on nobody's
  timetable, while this one is wrong precisely in the hours after a release,
  which is when somebody is still around to finish the job. A failure opens an
  issue and a later one comments on it; the run is where the detail lives.

  Three things are enumerated rather than inferred. The **state vocabulary** is
  closed, so a row whose state nothing recognises is a failure and not a row
  quietly skipped — `cut, never published` is 1.10.0's and cannot become the
  escape hatch every awkward release takes. **`gh` failing to authenticate is a
  refusal**, because an unauthenticated `gh` reports no releases at all and that
  is indistinguishable from a repository with none. And the **GitHub-release
  floor is 1.0.0**, measured: of the 0.x line only `v0.6.0` has one, so
  demanding them of `v0.1.0` would fill the output with history and a check
  whose output is known-bad entries is one nobody reads.

  It deliberately does not check that the artefact is the *right* one.
  `verify-release` is that check.

## Fixed

- **`verify-release` has no standing failures** (R2). It had two, from the day
  each version was published, and nothing read either.

  **v1.9.0: five crates differed in `Cargo.lock`, and the cause is a claim with
  a shelf life.** `cargo package` strips the `path` from an intra-workspace
  dependency and resolves the registry requirement instead, so packaging
  `ucal-civil` records whichever `ucal-core` satisfies `^1.9.0` *at that moment*.
  In August that was 1.9.0, because nothing newer existed; today it is 1.11.0.
  Four lines differ, all one `[[package]]` block, and `ucal-core` still matches
  to the byte because it is the one crate with no sibling to resolve.

  So **`cargo package` is not reproducible for this workspace** from the moment
  a later compatible version is published. 1.9.0's notes recorded
  byte-reproducibility measured across 1.8.0; the measurement was right and
  nobody stated that it expires. The comparison now normalises exactly those
  entries and compares everything else verbatim — a third-party version moving,
  or a sibling's *dependency list* changing, still fails, and four tests say so.

  **v1.11.0: six crates differed in `.cargo_vcs_info.json`**, because it
  published from the cut commit while the tag sits on the merge. Enumerated
  against that one version with its reason, the shape the retired signing key
  got — a blanket exemption would leave the next release free to repeat it
  unnoticed. A test asserts every entry names a single version and carries a
  reason.

  The reason prints **once**, as a legend, rather than on each of six lines: a
  paragraph repeated until it is scenery is how a standing failure goes unread.

- **A command reaches the `ucal-json/1` promise by more than being remembered**
  (R3), and the check found one that had not.

  Two hand-maintained lists enumerate the same commands — `commands()` in
  `json_surface.rs` and `all_commands()` in `manual_fields.rs`. The existing
  `the_baseline_covers_every_command` asserts every *listed* command
  contributes, which is the weaker half. Nothing asked whether the list was
  complete, and 1.11.0 found that out the only way then available: `add --in`
  was added to one list and the *other* file failed.

  `check-docs`'s eleventh check reads the commands from `main.rs` — subcommands
  included, because `cal export` arrived in 1.10.0 and a check stopping at the
  top-level `cal` would have had nothing to say about it. Each must contribute
  to the surface baseline or be listed as emitting no document, **with a
  reason**.

  **On its first run it found `cal export`**, which emits an HJSON body file
  because a generator's output is an input to something else. Legitimately
  absent — and until now a legitimate absence and an oversight looked identical
  to every check in the tree. `CLI.md` now says so, as `seq`, `man` and
  `completions` already did.

  Checked in both directions: an entry for a command that does not exist fails,
  and so does one for a command that turns out to contribute. The corpus gained
  the mutation that proves the second — **24 mutations, none surviving**.

## Internal

- Workspace and all seven packages at `1.12.0`.
- **J2000.0 is derived rather than pasted.** `body_file.rs` carried it as a
  61-digit literal since 0.9.0. It was correct — a test asserts the derivation
  reproduces exactly the digits that were there — and a committed copy of a
  value the code can compute is one edit from not being, which is what P2 found
  in the book's diagnostics appendix. A1 gave the code a way to compute it.
- **The Julian Date conversions are checked against an independent
  implementation** (D). Every claim A1 made about exactness was checked by A1's
  own arithmetic, where a matched pair of errors would cancel and pass.
  `hifitime` is a different author working from the standards rather than from
  this code, and is already a dependency under a permissive licence. `S1`
  assessed `siderust` for the same job and rejected it — AGPL-3.0-only against
  MPL-2.0 settles it before `f64`, `std`-only and 351 kSLoC each settle it
  again.

  **The oracle is one-directional and says so.** `hifitime` returns `f64` days,
  and a Julian Date near 2 460 000 has ~2 µs of representation spacing in a
  double, so it cannot check this crate past that. It catches a wrong epoch, a
  wrong day length, a scale applied backwards and an off-by-one in the MJD
  offset; it cannot catch a sub-microsecond error and nothing available could.

  **Its first version had a hole, found by injecting.** It looped over scales
  while converting forwards in `Tt` every time, so the TAI offset cancelled on
  both sides and the loop compared one path with itself — the classic 64.368 s
  sign error passed it. It now compares the input date against the oracle's
  reading of the instant produced, in the named scale, which exercises both
  directions. An oracle that passes on a broken implementation is worth less
  than no oracle, because it is also a claim.
- **A round-trip test found a real defect in B before it shipped.** `cycle_at`
  compared instants against `time_of(e).window.lo()` — a window *edge*, which
  sits `k·σ` from the centre, and σ grows with `|E|`. The comparison therefore
  drifted by whole cycles the further out it looked, and the test caught it at
  cycle −999 where 1σ is ten periods wide. A window edge is not a time.
- **R3's check caught A1 the day A1 was written.** `from-jd` and `to-jd` emit
  documents and were not in either hand-maintained list; the check reported both
  before any test did. Adding them then failed `manual_fields` on `mjd`, a field
  named for a flag that every listed invocation passed as `false` — so a second
  invocation exercises it. That is the check working twice in one commit, on the
  feature written three commits after it.
- **The release procedure has a fourteenth step**: `check-releases`, run at the
  point the Contents row is written rather than only on the daily schedule. The
  gap it closes is the hours between writing `released` and its being so.
