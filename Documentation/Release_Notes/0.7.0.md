# 0.7.0 — UNRELEASED

In development on the `0.7.0` branch. `main` carries the released 0.6.0 line.

## The goal of this cycle: the surface meets someone who is not the author

This is the only cycle whose success is not in the author's control, and the one
that decides whether 1.0 is honest.

Six releases have refined a design against a single set of assumptions. The API
has never been used by anyone but its author, so every breaking change so far
cost nothing — which means **none of them tested whether the surface is right**,
only that it could be changed.

The project's own argument is that what nobody checks, drifts. That applies to
this repository's design as much as to its arithmetic, and it is the one form of
checking that cannot be automated.

### What this cycle can and cannot do

It cannot make contact happen. What it can do is **remove every obstacle between
an interested stranger and a completed task**, and then wait — which is most of
what has landed so far.

### Scope

**C1 — One external implementation reproducing the conformance vectors.**
Not a user of these crates: an independent implementation of UC-1 that computes
the constants its own way. That is what the vectors and their signature are
*for*, and until one exists the conformance apparatus has never been used.

**C2 — GE-A4, the two-reader test.** Carried since 0.2.0. The book's
dual-audience claim is untested; the protocol is written and has a kill
criterion, so a negative result is a real outcome.

**C3 — One person using the CLI for something.** The `--bridge` default, the
certification vocabulary and the promoted-column layout are all guesses about a
reader who has never existed.

**C4 — Record what contact changes**, including "nothing", and treat breaking
changes as the cycle's product rather than its cost. A 1.0 that ships without
ever having been wrong about its surface has not learned anything.

### Done when

At least one of C1–C3 has happened and its findings are recorded. **If contact
proves impossible, the honest outcome is that 1.0 does not ship** and the crates
stay `0.x` — which costs nothing, since `0.x` already permits everything 1.0
would and promises less.

### Explicitly not in scope

- **New features.** A cycle spent waiting is the wrong cycle to widen a surface
  that 0.6.0 just finished enumerating.
- **Shipping 1.0 on a schedule.** The version number is a promise about
  compatibility. Reaching it because the project feels finished is the same
  category error as reporting a midpoint because an interval is inconvenient.

## Breaking

_none yet._

Expect contents, and treat them as the point. 0.8.0 exists to spend what this
cycle earns; a finding that arrives after 1.0 has to wait for 2.0.

## Added

- **[`Documentation/CONTACT.md`](../CONTACT.md)** — three specific asks, each
  with what to do, how long it takes, what to report, and what happens to the
  answer. Specific on purpose: "contributions welcome" gets nothing, and
  deserves to.

  C1 is stated so it can be done in **thirty minutes, in any language, with no
  Rust and nothing to install** — compute three integers and compare decimal
  strings. The barrier to the most valuable thing this project can receive was
  previously "read a 90-page specification first".

  Each ask names the outcome that is worth *more* than success. For C1 that is
  **"I could not tell what to compute from the documents"**, because it says the
  specification is not self-contained and this repository cannot discover that
  from the inside.

- **Issue templates** for C1 and C3, with the expected values inline, and a
  `config.yml` pointing at `CONTACT.md` and `CONFORMANCE.md`.

- **The signing key is published outside this repository.** It is now in the
  READMEs of `ucal` and `ucal-core`, which crates.io and docs.rs render from a
  package tarball that **cannot be edited once a version is published**, and in
  the repository README, `CONTACT.md`, `CONFORMANCE.md` and the 0.5.0 notes that
  announced the signing.

  What that is worth is stated rather than implied, because the temptation here
  is to treat five copies as five reasons. **It is not five independent trust
  paths** — one person placed all of them, and against a forgery a reader is no
  better off than with one. What it buys is that two copies are beyond the
  author's own reach once released, so a key **changed** in this repository, by
  compromise or rewrite or coercion, can be contradicted by an artefact nobody
  can quietly edit. That is tamper-evidence after the fact.

  **First contact is still trust on first use**, and copies do not fix it. That
  needs an authority which is not this project — a DNS record under its own
  registrar, a third party signing this key with theirs, or publication with an
  editorial record. `CONFORMANCE.md` says so plainly instead of letting the
  count do the arguing.

- **`signing-key` check.** Every declared publication must carry the key, and no
  document in the tree may carry a *different* one. The realistic failure is a
  truncated paste or a transposed character, not a forgery — and a reader who
  checks a mistyped key learns nothing while believing they learned something.

  It found one on its first run: the 0.5.0 notes named the key ID and never
  printed the key, so a reader of the release that announced signing could not
  check the thing being announced.

- **`contact-constants` check.** `CONTACT.md` and the C1 template quote `BEAT`,
  `SECOND` and `ORIGIN_OFFSET` so a stranger need not open the vector file
  first. That convenience is a copy, and a copy drifts — this one would drift
  into **asking someone to reproduce the wrong number**, wasting the scarcest
  resource this project has. `check-docs` now fails if either file names a
  constant without quoting the value in `fixtures/vectors.json`.

- **[`GE-U4-walk.sh`](../Proposals/GE-U4-walk.sh)** — the tier-scale navigator's
  cheapest test, built. Forty-five frames, one per tier, stepping on Enter or
  playing on a timer: the ladder travelled rather than tabulated. Sixty lines of
  shell against `ratatui` and `crossterm`, which is the ratio the proposal was
  betting on when it named this the thing to try first.

  It computes nothing — every frame is read from one `ucal ladder --json`
  invocation, so the walk and the table it is compared against are the same Doc
  at the same revision.

  Building it already found something. The first version walked the `beats`
  column and the **first twelve frames all read `0`** — every tier below the
  beat is under one beat, and six fractional digits cannot show it. It now
  counts ticks, where each tier is exactly `5^e` and the number grows from one
  digit to a hundred and fifty-four. That is a better frame than the one
  intended: the reader watches a *shape* fill the screen instead of reading a
  value.

  It is not the experiment. The kill criterion needs two readers, and the author
  cannot be either. What was in the author's control was making it runnable.

## Changed

- **[`ROAD-TO-1.0.md`](../Proposals/ROAD-TO-1.0.md) gained a 0.9.0**, because
  the plan contradicted its own exit criteria. They require **two consecutive
  releases with no breaking change**; the five cycles supplied at most one, since
  0.8.0 is defined as the cycle that *spends* 0.7.0's breaks. Reading
  "0.8.0 → 1.0.0" as satisfying that was an arithmetic error in the gate, and a
  gate that cannot be met is a gate that gets waived.

  0.9.0 has nothing to build, which is the point: a cycle whose diff has no
  `Breaking` section is evidence the surface has stopped moving, and that
  evidence cannot be manufactured by working harder.

- **What happens if contact never comes** is now written down, because "never"
  is a likely outcome here and an open-ended wait is not a plan. Two things,
  kept separate: **the contact gate stays shut** — `0.x` forever is an honest
  resting state and a version number is not a reward for effort — and **the
  cycles do not stop**. 0.7.0 closes and ships like any other with its finding
  recorded as *no contact yet*. Holding the branch open until a stranger arrives
  would make the repository look abandoned to exactly the stranger it is waiting
  for.

- **D5's Titan search was run**, and the reason for the missing anchor changed.
  Details in `Fixed` below, since two of the three things the 0.4.0 entry
  assumed turned out to be wrong.

## Fixed

- **`anchors.rs` said something about Titan that is not true.** It claimed
  *"there is no established prime meridian convention with a published epoch for
  Titan comparable to UT1 or Mars24."* The literature search
  [D5](../Proposals/D5-titan-anchor.md) specified — and which 0.4.0 recorded as
  not performed — has now been run, and there is one: the IAU WGCCRE rotational
  elements, `W = 186.5855° + 22.5769768°/day` from J2000.0 TDB, distributed in
  NAIF's `pck00011.tpc`.

  Two of the three assumptions behind the entry were wrong.

  **The convention exists** — but for the wrong quantity. It says where Titan's
  prime meridian points, not when it faces away from the Sun, and the anchor's
  phase is the second thing. No Mars24 counterpart was found; the Huygens
  landing, the one event that could have seeded one, is reported in UTC.

  **The width is not the obstacle.** Titan's rotation is measurably
  non-synchronous, so the disagreement between published models is itself a
  defensible uncertainty: 0.12°/yr (Stiles et al. 2010, correcting their own
  0.36°/yr of 2008) over 26.6 years is about 3.2°, which at 22.5769768°/day is
  **3.4 hours — under one per cent of a Titan solar day.** GE-3 asked whether an
  anchor could be established to a window narrower than one local solar day; for
  Titan the answer is now *yes, by two orders of magnitude*, if it could be
  established at all.

  What actually blocks it is now specific: **the last step is an ephemeris
  evaluation this project does not perform.** Going from `W(t)` to a phase needs
  the Sun's direction from Titan, hence DE440 and a Saturnian satellite kernel.
  `ucal-body` carries cited parameters and derives from them; it does not
  integrate orbits. And deriving it here would make this repository the
  *publisher* of Titan's solar-time convention rather than a citer of one, which
  is the claim §19.4's `Kind` distinction exists to keep out.

  `titan-d` is unchanged — still `UCAL-E0062`, still complete in units and
  incomplete in phase. What changed is that the entry is now falsifiable by one
  publication instead of resting on an unperformed search.

  One incidental confirmation: the IAU rotation rate implies `360 / 22.5769768 =
  15.945421` days, exactly the rotation period `data::titan()` already carries
  from the NASA fact sheet.

- **The 1.0 exit criteria asserted something false about themselves.**
  `ROAD-TO-1.0.md` listed *"CI green on every push, with no known-failing job"*
  as met "0.5.0 onward". The `features` workflow failed on every push it ever
  ran, including the 0.6.0 release tag. The criterion was written, nothing
  checked whether it held, and the document asserted it did — the exact failure
  the table exists to keep out, occurring in the table.

- **The `features` workflow had never passed.** It went red on every push since
  0.6.0 added it, including the release tag, and the failing assertion was the
  one checking that enabling both backends reports the guard's sentence *first*.

  The guard was correct throughout. The check could not see it: the workflow
  sets `CARGO_TERM_COLOR: always`, so every diagnostic arrives as
  `ESC[1mESC[91merrorESC[0m: …` and the anchored `grep "^error"` matched
  nothing. It passed locally, where cargo writing to a pipe emits plain text,
  and failed in CI for a reason the log did not contain — the failure branch
  printed only the empty line it had extracted.

  The `refused` job now sets `CARGO_TERM_COLOR: never`, because a job that reads
  cargo's output as text has to ask cargo for text, and the failure branch
  prints the whole output. Verified by running the assertion under both settings:
  it passes under `never` and still fails under `always`, so the fix is the
  cause and not a coincidence.

  **This is the third time the shape has appeared** — after the false MSRV and
  the three accidentally-unsupported feature combinations. A check that has
  never been observed passing is not yet a mechanism. This one at least failed
  loudly; a red CI nobody reads is how the next one gets to be green and wrong.

## Carried forward from 0.6.0

- **The public key still has no authority behind it that is not the author.**
  Partly addressed above: it now appears in artefacts that cannot be edited
  after publication, which makes a later change detectable. What remains is the
  part copies cannot buy — a DNS record, a third-party signature, or a venue
  with an editorial record. Until then, first contact is trust on first use.
- **Titan has no anchor**, and the search specified in
  [`D5-titan-anchor.md`](../Proposals/D5-titan-anchor.md) has not been run
  against the literature.
- **The tier-scale navigator** remains a proposal with a kill criterion, and its
  cheapest test — a recorded walk rather than an interactive program — has not
  been tried.
- **Eight commits in the history are unsigned**, permanently.
